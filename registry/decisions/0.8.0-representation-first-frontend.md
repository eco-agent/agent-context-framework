# Registry 0.8.0 — representation-first frontend discipline

Registry `0.8.0` replaces the frontend skill's implementation-anchored linear
workflow with a progressively disclosed representation-search and reconciliation
workflow. The 30-component topology and every dependency edge remain unchanged.

## Decision

- Treat existing implementations and schemas as evidence rather than default
  interface representations. Substantial frontend work settles the product job,
  observed states, representation thesis, and composition before reading current
  component boundaries as implementation constraints.
- Treat desktop and mobile as projections of one product model. Each mobile surface
  records `preserve`, `adapt`, `recompose`, `split`, `replace`, or `remove`, with no
  default preference for preservation or visual parity.
- Search materially different representations before implementation. Alternatives
  differ in their representation or interaction thesis. At least one candidate does
  not display the source value. The first acceptable design remains a draft until a
  major decision is removed or replaced and compared across the same states.
- Prefer observed rendered states, representative runtime data, and user tasks over
  type and schema names when selecting presentation. Data may drive behavior,
  atmosphere, composition, sound, motion, visibility, hierarchy, or narrative
  without becoming a separate widget.
- Keep `frontend-design-discipline/SKILL.md` as the stage router. Focused references
  own product reframing, representation search, mobile recomposition, progressive
  contextualization, implementation reconciliation, and visual review.
- Separate exploration evidence from the approved frontend specification. The
  approved specification is a deliberately lossy downstream interface and excludes
  discarded alternatives and exploratory discussion.
- Keep responsive CSS in `responsive-css-architect`. It expresses layout
  relationships through intrinsic constraints and treats fixed values as intentional
  physical constraints rather than screenshot compensation.

## Protected semantics

- `representation-before-implementation`
- `observed-state-before-schema`
- `materially-different-representation-search`
- `mobile-product-projection`
- `lossy-stage-artifacts`
- `implementation-as-reconciliation`
- `relationships-before-measurements`
- `context-isolation-claim-boundary`

## Context boundary

The skill can route stages, name allowed context, exclude known anchors, and pass a
reduced artifact forward. It cannot guarantee that a worker has forgotten inherited
conversation or cannot rediscover repository context.

Hard progressive contextualization remains additional work. It requires fresh
workers, exact context manifests, scoped filesystem/retrieval/tool authority, and an
exposure audit. Minimum sufficient context remains an empirical target established
through representative and adversarial evaluation, evidence-backed escalation, and
input ablation. This revision does not claim either property programmatically.

## Preserved boundaries

- No component, bundle, dependency edge, capability declaration, or license changes.
- No objective kernel, context controller, task envelope, scheduler, queue, database,
  binding producer, adaptive hierarchy, or active Codex execution is added.
- No automated check claims to judge metaphor coherence, usefulness, visual taste,
  or globally minimal context.
- Historical decisions remain unchanged.
- No consumer manifest or lockfile edit, migration, publication, deployment, or push
  is introduced.
