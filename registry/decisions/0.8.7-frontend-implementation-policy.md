# Registry 0.8.7: frontend implementation policy

Registry `0.8.7` closes three implementation gaps that caused agents to bypass
installed component libraries, replace Tailwind utilities with growing raw CSS
stylesheets, and tune typography with arbitrary local metrics.

## Status

Accepted.

## Decision

The frontend component requires agents to inspect and reuse the project's
component system before creating replacements. A component library does not
choose product structure, visible copy, or hierarchy. When an approved role
matches a library component, that component retains ownership of its behavior
and accessibility unless its public API cannot meet a recorded requirement.

In projects that select Tailwind, Tailwind utilities represent every style the
framework can express cleanly. Repetition, class-string length, and stable
component roles do not justify moving styles into ordinary CSS rules. CSS files
may contain Tailwind directives, base rules, unsupported selectors, properties,
or at-rules, and rules for third-party markup that cannot receive utility
classes. Responsive CSS guidance decides relationships and behavior without
overriding this representation choice.

Typography uses named roles from the established type system. Agents keep the
line-height paired with the role or Tailwind text-size utility and leave ordinary
tracking at `normal`. A local line-height or tracking exception needs an approved
source or a measured rendering defect. Variable-font ranges do not authorize
invented weights.

Frontend hierarchy starts with established type roles, spacing, weight, color,
and elevation. A border or divider needs a structural, grouping, state, or
interaction reason. Agents must not add muted one-pixel separators to compensate
for weak hierarchy.

## Owners

| Decision | Owner |
| --- | --- |
| Component discovery and reuse | Base frontend policy and `frontend-design-discipline` |
| Accessible component behavior | `design-accessible-interfaces` |
| Tailwind representation and raw CSS exceptions | `tailwind-css-architect` |
| Typography roles and metric exceptions | `design-web-typography` |
| Protected model-facing meaning | Context governance |

## Consequences

Agents must inspect installed component systems before writing replacements.
Tailwind projects should no longer accumulate ordinary component and page CSS
merely because utility recipes repeat or use variants. Existing component-library
recipe helpers remain valid instead of being replaced by semantic CSS classes.

Typography changes happen at the role definition. Per-heading arbitrary leading,
tracking, and intermediate variable-font weights are rejected unless recorded
evidence requires the exact value. Decorative separators no longer act as a
default hierarchy treatment.

This decision does not add component-parameter custom properties to responsive
CSS and does not add `responsive-css-architect` to the base frontend component.
Those changes remain separate so their guidance can build on these boundaries.
