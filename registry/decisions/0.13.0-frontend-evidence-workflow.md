# Registry 0.13.0 frontend evidence workflow

Revision `0.13.0` makes visual evidence and stage ownership part of the installed
frontend design discipline.

## Decision

Frontend work completes the approved design stage. Foundations, component
contracts, interaction recipes, application shells, failure systems, product
assembly, and rendered acceptance each own different decisions and may each be a
complete task result. The general cross-layer slice rule begins at product
assembly. It does not require placeholder routes, fake data, or premature product
structure during earlier design stages.

When captures, clips, runnable studies, or accepted and rejected examples decide
the visual direction, preserve the inspectable evidence in a durable project-owned
path. Each retained item records an exact region or interaction, the lesson it
establishes, and what the project must not copy or infer. A still image does not
prove motion.

Add a component lab contract for representative fixtures, applicable product
states, interaction and accessibility behavior, supported placements, themes,
containers, and rendered evidence. Unsupported required cells block promotion.
Humans own visual judgment and accept exact evidence hashes at one Git revision.

## Ownership and observation

- `frontend-design-discipline` owns stage selection and routes focused detail.
- `frontend-stages.md` owns stage boundaries and promotion gates.
- `precedent-evidence.md` and `visual-evidence.md` own visual calibration records.
- `interaction-studies.md` owns runnable behavior studies.
- `component-lab.md` owns reusable component acceptance evidence.
- The frontend specification binds approved evidence and the delivery stage to
  implementation.
- Registry projection installs the complete skill directory. Context governance
  protects the new semantic requirements and exact source hashes.
- Existing frontend workflow controllers remain optional. They continue to own
  bounded render, reviewer repair, and external human acceptance when selected.

## Grace paths

- If source bytes cannot be stored, retain the source location, exact region,
  annotations, derived lesson, and storage restriction. Report that offline
  inspection is unavailable.
- If motion evidence is absent, mark motion unverified and keep the result static.
- If a later stage discovers a false assumption, return the evidence to the stage
  that owns the decision instead of rewriting the contract downstream.
- If required component-lab cells remain unsupported, stop promotion and report
  them. Do not invent product fixtures.
- If rendered evidence is ready but human judgment is unavailable, stop at human
  review. An agent cannot accept its own visual result.

## Retained behavior

- Representation still precedes substantial implementation.
- Product-specific precedent does not become universal framework taste.
- Licensed implementation adoption still follows `adopt-established-product`.
- The current component system retains behavior and accessibility ownership unless
  its public API cannot meet a recorded requirement.
- Materially different representation and rendered comparisons remain required at
  their existing decision points.
- Ordinary implementation still completes one cross-layer slice.
- The general work-record template routes staged frontend work to its current
  design stage and promotion gate.
- Browser tooling and capture commands remain project-owned.

## Rejected alternatives

- More abstract visual adjectives would repeat the failure. They cannot show what
  a later agent should inspect.
- Storing Business Operating System screenshots in ACF would turn one product's
  taste into global policy and create unclear reuse rights.
- A new screenshot dependency would duplicate project capture tooling and the
  optional frontend workflow adapter boundary.
- Requiring a deployable path from every frontend task would pull product decisions
  into foundations and component work before those decisions have an owner.

## Reuse assessment

The existing ACF frontend workflow remains the runtime owner for render evidence,
screenshot hashes, bounded reviewer repair, and exact external acceptance.
Project adapters continue to own binary artifacts and browser capture.

Storybook Component Story Format provides a useful optional mapping for named
component states, args, and interaction recipes. Storybook uses the MIT license.
Playwright screenshot and trace formats provide a useful optional mapping for
capture environment, ordered actions, DOM snapshots, console output, and network
activity. Playwright uses the Apache-2.0 license. ACF copies no source from either
project and adds no dependency. The installed templates describe an adapter
contract that projects may satisfy with the tools they already use.

The assessment used the [Storybook CSF documentation](https://storybook.js.org/docs/8/api/csf/index),
the [Storybook license](https://github.com/storybookjs/storybook/blob/next/LICENSE),
the [Playwright visual comparison documentation](https://playwright.dev/docs/next/test-snapshots),
the [Playwright trace documentation](https://playwright.dev/docs/next/trace-viewer),
and the [Playwright license](https://github.com/microsoft/playwright/blob/main/LICENSE)
on 2026-08-27.
