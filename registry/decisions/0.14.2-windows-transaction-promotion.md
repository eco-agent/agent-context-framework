# Registry 0.14.2 Windows transaction promotion

Revision `0.14.2` carries bounded Windows staged-write recovery into the
package-free capsule bootstrap. It preserves the `0.14.1` component graph,
artifact paths, schemas, and runtime selection.

Windows can return `EPERM` when another process briefly holds an existing target
file open. The context transaction now retries only that error from the
staged-write rename. It waits 100, 200, and 300 ms between attempts, matching
Node's established linear filesystem retry delay. Before every retry, it proves
that the staged file still has the journaled after hash and the target still has
the before hash. If the target already has the after hash and staging is gone,
promotion is complete.

Any other error or state change still fails immediately. A target locked beyond
600 ms produces one terminal error with the last `EPERM` as its cause. The
published journal and staged bytes remain available to the existing doctor and
recovery path.

The source transaction tests use a real open Windows file handle. One test
releases it inside the retry window and requires success. Another holds it past
the limit, requires a resumable transaction, closes the handle, and completes
recovery. Existing drift, symbolic-link, interruption, and bundle
reproducibility tests retain their roles.
