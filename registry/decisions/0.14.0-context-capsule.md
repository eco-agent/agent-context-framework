# Registry 0.14.0 context capsule

Revision `0.14.0` adds the format and policy contracts needed to compress a
selected ACF closure into one tracked file.

## Decision

ACF uses one deterministic `acf-capsule-v1` file per project. The capsule keeps
the resolved component definitions, exact registry source bytes, licences,
attribution, and hashes. Startup instructions, Codex configuration, project
configuration, project policy, and other activation files remain expanded.

The first deployment stage writes `.agent-context/capsule.acf` beside the current
expanded installation. Lock v2 remains authoritative during this stage. ACF does
not remove expanded files or write lock v3 until generated clean and dirty apps
prove that the capsule reconstructs the same installed scopes.

Lock v3 has its own schema constant. Registry v2, project config v2, and
installation lock v2 keep their current decoder and version. The capsule-aware
validator owns relationships between lock v3 and a decoded capsule.
Lock v3 keeps tracked expanded activation separate from ignored materialization
ownership. The materialization records bind exact generated paths and hashes to
the capsule. An ignored receipt may report that state, but cannot authorize a
deletion.

Fresh projects receive `*.acf binary` in the seeded `.gitattributes`. The seed
still belongs to the project after its first creation. A later migration must
preserve existing project attributes and add the capsule rule through a bounded
transaction when the effective Git attributes do not already mark it binary.

## Ownership and observation

- The registry resolver owns the dependency-first component closure.
- The capsule builder owns canonical serialization, compression, and exact
  source-byte inclusion.
- The capsule reader owns complete verification before inspection or extraction.
- Lock v2 and the expanded installer remain the installation authority during
  side-by-side proof.
- Lock v3 records capsule identity and expanded activation scopes after the
  migration checkpoint.
- The generated test application owns clean, dirty, expanded, and side-by-side
  acceptance states. Its materialized state selects `skill-diagnose` and writes
  the verified ignored projection to `.agents/skills`.
- The materialization receipt owns the capsule identity and exact generated file
  hashes. It does not authorize replacement.
- Core installs a tracked `.agent-context/bootstrap.mjs`. The committed bundle
  rebuilds from a dedicated TypeScript entry with the pinned `vite-plus` packer.
  It needs Node and Git, not a project package install.

## Recovery

- A malformed or inconsistent capsule is rejected without writing project files.
- Capsule build refuses to replace an existing output.
- Side-by-side verification reports exact mismatches and leaves lock v2 and the
  expanded targets unchanged.
- Initial skill materialization writes through the existing recoverable file
  transaction. ACF-owned skill directories include the full component content
  digest. An exact rerun writes nothing. Modified, unexplained, or
  different-capsule output blocks replacement and keeps the expanded tracked
  installation available. The ignored receipt never authorizes deletion without
  tracked ownership evidence.
- Materialization blocks before writing when Git does not ignore the receipt or
  any generated skill target. The standalone bootstrap recovers safe transaction
  state first and reports blocked recovery once at its process boundary.
- Fresh clones require the explicit
  `node .agent-context/bootstrap.mjs materialize` command before Codex starts.
  Git cannot provide a portable automatic post-clone step.
- Existing project `.gitattributes` content remains untouched in this stage.
- A future capsule and lock update must share one binary-safe transaction. ACF
  will not publish those two files through separate writes.

## Retained behavior

- Project component selection remains inspectable in
  `.agent-context/config.json`.
- Project policy remains expanded and project-owned.
- Registry sources retain their exact hashes, licences, notices, and provenance.
- The current installer keeps its local-edit detection, structured projection,
  transaction journal, and recovery behavior.
- An ordinary clone remains self-contained once capsule materialization ships.

## Rejected alternatives

- A submodule adds clone setup and another repository trust boundary.
- A package dependency makes an ordinary clone incomplete before installation.
- One capsule per component creates more tracked files without a measured review
  or update benefit.
- Replacing expanded files before equivalence removes the working recovery path.
- Writing a capsule and lock in separate operations permits a partial pair after
  failure.

## Verification

The capsule format, corruption checks, semantic commands, clean reconstruction,
dirty-work preservation, initial skill materialization, reproducible plain-Node
bootstrap, v2 installer behavior, and lock-v3 ownership separation have focused
automated coverage. The final revision and repository profile results are
recorded when this registry update closes.
