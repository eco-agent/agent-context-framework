# Precedent evidence

Use this reference when visual material influences a frontend decision. A phrase
such as `quiet structural planes` is not evidence. Preserve the capture, clip, or
runnable study that made the phrase concrete.

## Separate observation from adoption

An observation source can teach composition, density, material, feedback, or
motion without authorizing copied code, branding, content, or product structure.
Record the lesson and the limit together.

Licensed source selected for topology or implementation follows
`adopt-established-product`. Keep its revision, license, source receipt, and file
mapping. Do not treat a screenshot of a commercial product as reusable source.

## Record an exact lesson

Give every retained artifact an evidence ID. Record its repository path, source,
capture context, and exact region or interaction. Then state four things:

1. What is visibly present.
2. What behavior or relationship the artifact establishes.
3. Which project decision may use that lesson.
4. What the project must not copy or infer from it.

Use coordinates, an annotation ID, a timestamp range, or a named study state to
identify the relevant part. A whole-page citation leaves too much room for model
priors.

For an accepted example, name the lesson that should survive. For a rejected
example, name the boundary it proves. Do not retain discarded exploration that
has no continuing decision value.

## Preserve motion honestly

A still image proves one frame. It does not prove how controls appear, how a
selection settles, how layout moves, or how focus returns. Support a motion claim
with a clip, ordered frames, or a runnable study. Record the starting state, user
input, intermediate feedback, settled state, timing that carries meaning, and the
reduced-motion result.

If no motion evidence exists, mark the behavior unverified. Keep the result static
until an authorized owner supplies or approves a motion decision.

## Promote accepted evidence

Working files may begin under `.codex/work/frontend`. Before closing the design
task, move every accepted artifact and its record to a durable project-owned path
named by the specification or a project contract. Preserve the original bytes
when possible. Record a content hash or the Git revision that fixes those bytes.

Prefer a path already owned by a project contract or an established documentation
root. If neither exists and the user has not authorized new repository structure,
keep the working evidence under `.codex/work/frontend` and report that promotion
is blocked. Do not create a new documentation hierarchy as an incidental part of
evidence capture.

The durable record should contain:

- raw captures, clips, or links to licensed source;
- annotations or exact regions;
- accepted lessons and prohibited imitation;
- runnable studies that still define behavior;
- accepted and rejected comparisons that still define a boundary;
- provenance, capture context, theme, viewport, and date;
- media type, byte count, SHA-256, locale, device pixel ratio, capture adapter,
  permission or license, and redaction policy;
- the human owner who accepted the lesson.

If policy forbids storing the source bytes, retain the source location, exact
region, annotations, derived lesson, and storage restriction. Report that later
agents cannot inspect the original artifact offline.
