# Observable model-prior hypotheses

Use these as falsifiable hypotheses, not personality labels or claims about hidden reasoning.

## Completion bias

Signal: the agent continues past an explicit authority or product-decision gap to produce a complete-looking result.

Competing explanation: the missing choice was safely inferable from accepted architecture.

Guard: encode authority limits in preflight or require a typed stop outcome.

## Architecture completion bias

Signal: a bounded slice grows into a generic framework, shared abstraction, or full platform layer.

Competing explanation: the supposedly local mechanism has several already-approved consumers.

Guard: require named current consumers and deleted local code before accepting shared machinery.

## Stale-context anchoring

Signal: narration, old handoffs, or accepted ADRs are treated as evidence that code or current state exists.

Competing explanation: the source was validated earlier in the same task and has not changed.

Guard: prefer executable inventory, exact revisions, and current implementation matrices.

## Context echo

Signal: objectives, constraints, and status are repeatedly restated without changing a decision or enabling verification.

Competing explanation: a long-running task needed a concise state checkpoint after compaction.

Guard: emit deltas and decisions; keep one durable checkpoint for resumability.

## Verification maximalism

Signal: full branch or runtime gates repeat after narrow changes that cannot affect those surfaces.

Competing explanation: the repository requires the gate before integration.

Guard: map changed paths to checks and reserve the full gate for integration.

## Happy-path confidence

Signal: implementation status is declared from successful ordinary execution while exhaustion, collision, rollback, or cleanup failure remains untested.

Competing explanation: failure evidence was explicitly deferred and the claim was narrow.

Guard: derive tests from claimed failure semantics before writing the handoff.

## Local-repair tunnel

Signal: repeated patches accumulate around one failing test without reconsidering the state model or ownership boundary.

Competing explanation: small independent defects share one integration surface.

Guard: after the second semantic repair, restate valid states and transaction owners before another patch.

## Framework reflex

Signal: the agent introduces a scheduler, parser, auth layer, or orchestration mechanism before inspecting pinned dependencies and repository implementations.

Competing explanation: existing mechanisms fail a documented conformance need.

Guard: run reuse review and record the missing semantic capability.

## Artifact inflation

Signal: plans, handoffs, capability files, and reports repeat the same information while no consumer or automated check uses them.

Competing explanation: the repository requires durable audit or long-horizon handoff evidence.

Guard: give every artifact one owner and consumer; generate mechanical facts where possible.

## Tool maximalism

Signal: broad searches, full output reads, screenshots, or repeated task reads are used before a bounded query.

Competing explanation: the repository or task was unfamiliar and no inventory existed.

Guard: query summaries first, expand only unresolved evidence, and add inventory tooling for recurring discovery.
